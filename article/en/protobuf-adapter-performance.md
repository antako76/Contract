# How We Made CONTRACT's Protobuf Adapter Faster Than Protobuf Itself

The same data in C++ almost always has to pass through several different
formats - debug output, YAML, binary, compact, protobuf - and without a
shared schema, each format grows its own field mapping, which drifts from
the others over time.

CONTRACT solves this with one declaration for all formats at once: the data
schema is declared once, directly in the type, and works at compile time -
no runtime reflection, no manual mapping per format:

```cpp
struct Customer {
    std::uint32_t id;
    std::string name;

    CONTRACT(Customer,
        (id, 1),
        (name, 2)
    )
};
```

That's the whole schema - no separate `.proto` file, no `protoc`, no
generated `.pb.h`/`.pb.cc` that you have to drag into the repository and
regenerate on every structural change. The same macro drives both the shape
of the C++ struct and the wire format underneath.

One of the adapters generates a protobuf-compatible wire format. We checked
it against real libprotobuf (3.21.12): byte-for-byte wire format identity is
confirmed across every measured scenario, including int32/int64 sign
extension. On speed - in most scenarios CONTRACT outperformed the code
generated by protoc and backed by libprotobuf: typically 0.3x-0.8x of the
time to pack and 0.4x-0.9x to unpack.

What follows are the specific engineering decisions behind that, and one
scenario where it didn't work out. Windowed I/O and dropping the
message-size pre-pass turn out to be the same decision: once you can write
straight into the window, there's simply no need to know the size ahead of
time. Separately - the one place where the size is still needed upfront
(the protocol itself requires it), and how that pass was made cheap. And
the last point isn't about writing at all - it's about how reading got rid
of the quadratic cost of looking up a field by number.

## How This Was Verified

The benchmark is `benchmarks/protobuf_reference_benchmark.cpp`, built
optionally (`-DCONTRACT_BENCH_WITH_PROTOBUF=ON`, so the main library and its
tests don't pull in protobuf as a dependency). It compares CONTRACT against
real libprotobuf on identical structs and data and checks the wire bytes
byte-for-byte - both sides running without errors doesn't prove anything on
its own.

Contentious spots were rewritten in several variants, run through Clang,
checked against the resulting assembly, and we kept whatever actually
measured faster - not whatever looked more elegant in the source.

Here's the full table across all 14 scenarios (Clang 19,
`--iterations 500000`, median of 15 independent runs on top of each run's
own median - so small effects don't drown in the noise of a single run).

nanoseconds per operation, `c/p` is the CONTRACT-to-protobuf ratio, `x` is
the ratio itself (above 1 means CONTRACT is slower):

Size matches in all 14 rows - that's the byte-for-byte wire format identity
mentioned above, not just for the "average" scenario but for every single
one measured.

One table of medians isn't enough to honestly say "faster" or "slower" -
results vary between runs. We computed that variance directly from the same
15 independent runs: the typical spread of the ratio between runs is
around ±8% of the median. We took that as the parity band - anything
within ±8% of 1.0 counts as "roughly even," not a win or a loss.

The tally across all 28 measurements (14 scenarios × pack/unpack): **20
confident wins for CONTRACT, 4 parity, 4 losses**. By scenario:

- **Won**: 9 of 14 rows on pack, 11 of 14 on unpack.
- **Parity**: `vector[25]`, `all_numbers[8]`, and `int25` on pack, `numeric`
  on unpack. `int25` on pack is a borderline case: at 5 runs it was
  slightly above the boundary (1.08), at 15 it's slightly inside (1.05).
  That's not a code change, just the estimate tightening with more samples.
- **Lost**: `vector[100]` and `bytes[32]` on pack; `vector[100]` and
  `int25` on unpack.

`int25` on unpack and `vector[100]` (both pack and unpack) are confirmed
losses: both are shapes with a large number of cheap elements and no
strings, which normally mask the per-element dispatch/decode cost.

## 1. Windowed I/O: Write Straight to Where the Data Belongs Anyway

The `contract::io` layer is a facade over different "window"
implementations: the same `prepare`/`commit` interface for writing (and
`peek`/`consume` for reading) is implemented both for a plain fixed buffer
(`contract::io::window_output`, `include/contract/io/byte_window.hpp`) and
for a growing network buffer on top of `boost::beast::flat_buffer`
(`include/contract/io/beast_window.hpp`) - that is, for writing straight
into a buffer that later gets written to a socket. The serialization
adapter doesn't know, and doesn't need to know, exactly what it's writing
into: a pre-allocated chunk of memory, or a buffer that grows on its own
as it's written to.

One direct consequence is that even encoding a single field manages
without an intermediate stack buffer and `memcpy`. The standard temptation when
encoding a varint is to collect the bytes in a temporary stack buffer,
then copy them into the output. Simple, but a `memcpy` with a size known
only at runtime doesn't get inlined by the compiler - so every call on
that path pays for a real function call where a dozen instructions could
have done the job.

Instead, the writer writes straight into the current window via
`prepare`/`commit`:

```cpp
// Write straight into the window instead of a stack buffer + memcpy
// (runtime-sized memcpy defeats inlining). 10 bytes always fits any
// 64-bit varint.
auto window = out_.prepare(10);
if (window.size() >= 10) {
    std::size_t count = 0;
    std::uint64_t v = value;
    while (v >= 0x80u) {
        window[count] = static_cast<std::byte>((v & 0x7fu) | 0x80u);
        ++count;
        v >>= 7;
    }
    window[count] = static_cast<std::byte>(v);
    ++count;
    out_.commit(count);
    return write_status::ok;
}
```

`prepare(10)` reserves up to 10 bytes in the output window (the max size
of a varint for a 64-bit value), the bytes are encoded straight into that
span, `commit` finalizes the count actually written. No intermediate
buffer, no copying.

There's a nuance: the encoding path itself (`write_varint_payload`) has to
stay small and inlinable, because it's called for every scalar field. But
the path for when the buffer runs out and writing has to go through an
intermediate buffer (a rare, "boundary" case) is, conversely, deliberately
marked `noinline`:

```cpp
// Forced noinline: this is the rare boundary-crossing path. Left to the
// compiler, its single call site gets it inlined back into
// write_varint_payload, which then grows too large to inline itself at
// its many call sites in a caller with lots of scalar fields.
[[gnu::noinline]] write_status write_varint_payload_fallback(std::uint64_t value) {
    ...
}
```

The logic is simple: this function has exactly one call site, so without
an explicit marker the compiler happily inlines it right back into
`write_varint_payload` - and after that, `write_varint_payload` itself
grows so large that it stops getting inlined at the places where it's
called many times over (a message with 25 fields, for example). The
explicit `noinline` keeps the hot path small at the cost of one rare
function call on the cold path.

## 2. Corollary: No Pre-Pass Over the Message Size

Many serializers first compute the final message size, then allocate a
buffer of that size, then serialize. That's necessary when the write
destination is a fixed-size chunk of memory that has to be allocated in
advance.

But if you can write straight into a window that's either already big
enough or can grow on its own as you write (see point 1), that necessity
disappears on its own - there's no need to know the final message size
before you start writing it. So CONTRACT writes fields as it walks the
contract, with no separate "compute first, then write" pass:

```cpp
template<class Object, std::size_t Index>
write_status write_message_by_index(const Object& obj) {
    using object_type = std::remove_cvref_t<Object>;
    if constexpr (Index >= contract::field_count<object_type>()) {
        return write_status::ok;
    } else {
        auto descriptor = contract::field_at<Index, object_type>();
        const auto status = this->field(descriptor, obj);
        if (status == write_status::error) {
            return status;
        }
        return write_message_by_index<object_type, Index + 1>(obj);
    }
}
```

Each field is serialized right as it's visited - the compiler unrolls this
recursive template into a flat sequence of calls at compile time (`Index`
is a compile-time constant, `if constexpr` cuts away the rest before code
generation even happens).

## 3. The Exception: Nested Messages Still Need the Size Upfront

This works for serializing a value as a whole - regardless of whether the
window grows on its own or is already big enough. But protobuf as a format
has one exception that no window can get around: a nested message
(length-delimited) has to carry its byte length in front of it, which
means that length has to be known *before* the bytes themselves start
getting written. That's a requirement of the wire format itself, not of
the buffer, so there's no avoiding some kind of pass here in principle -
the only question is what shape it takes.

The solution is the same write path, just with a "mute" output that
doesn't write bytes but counts them:

```cpp
struct counting_output {
    void write(const void*, std::size_t size) noexcept {
        position_ += size;
    }
    // ...
private:
    std::size_t position_ = 0;
};

template<class Value>
std::optional<std::size_t> measure_encoded_size(const Value& value) {
    counting_output sizing{};
    writer<counting_output&> sizing_writer{sizing};
    using value_type = contract::adapters::base::clean_t<Value>;
    const auto status = codec<value_type>::write(sizing_writer, value);
    if (status == write_status::error) {
        return std::nullopt;
    }
    return sizing_writer.position();
}
```

`measure_encoded_size` runs the exact same `codec<T>::write` as the real
serialization does - there's simply no separate size-counting code that
could drift out of sync with the real write over time. The only
difference is where `counting_output` writes: not into a buffer, but into
a counter - bytes get added to the position instead of being stored.

There's one more detail here that saves real work: even varint encoding
for the size count isn't performed if all that's needed is a byte count -

```cpp
// counting_output only wants the byte count, not the actual bytes -
// skip encoding entirely instead of building bytes just to discard them.
if constexpr (std::is_same_v<std::remove_reference_t<Output>, counting_output>) {
    out_.write(nullptr, detail::varint_byte_count(value));
    return write_status::ok;
}
```

`varint_byte_count` is pure arithmetic (how many bytes the varint encoding
of a value will take), with no building of the actual bytes and not a
single branch:

```cpp
// Number of bytes a varint encoding of value takes up, without encoding it.
// byte_count = ceil(bit_width(value) / 7), value|1 folds the value==0 case
// (which needs 1 byte) into the same formula as value==1.
constexpr std::size_t varint_byte_count(std::uint64_t value) noexcept {
    const unsigned bits = 64u - static_cast<unsigned>(std::countl_zero(value | 1u));
    return (bits + 6u) / 7u;
}
```

A varint encodes a value in groups of 7 bits, so the byte count is
`ceil(significant_bits / 7)`. `std::countl_zero` (C++20, usually a single
hardware instruction like `lzcnt`/`clz`) gives the number of leading zero
bits, from which `64 - countl_zero(value)` is the position of the highest
set bit - which is exactly the "significant bits." `value | 1u` is a trick
for the `value == 0` case: without it, `countl_zero(0)` would give 64
leading zeros and 0 significant bits, but a varint for zero still has to
take up 1 byte; `| 1u` doesn't change the result for any nonzero value
(the low bit can already be occupied by anything anyway), but for zero it
turns it into 1, giving the same "1 significant bit → 1 byte" as for
value == 1. `(bits + 6u) / 7u` is integer round-up division by 7. All
told - no loops, no branches, usually one leading-zero-count instruction
plus a couple of arithmetic ones - where a naive version would count bytes
in a loop, repeating the `>>= 7` from the encoding itself.

## 4. Field Lookup by ID: From O(N²) to a Single Pass

The first three points are about writing. On the reading side there was a
separate, more glaring performance bug that surfaced not during
development but later, during profiling: field lookup by wire-format
number was written
as a recursive template that restarted the comparison from index zero for
every incoming field:

```cpp
template<class Object, std::size_t Index>
static read_status read_field_by_number(
    reader& in, Object& obj, std::uint32_t field_number, detail::wire_type wire)
{
    if constexpr (Index >= contract::field_count<Object>()) {
        // ... unknown field error ...
    } else {
        auto field = contract::field_at<Index, Object>();
        if (static_cast<std::uint32_t>(field.id) == field_number) {
            return in.read_field(field, obj, wire);
        }
        return read_field_by_number<Object, Index + 1>(in, obj, field_number, wire);
    }
}
```

For a message whose fields arrive in the wire format in increasing number
order (the usual case), this is a quadratic cost: reaching the last field
means comparing from the first one all over again each time. At 25
fields, this is no longer "almost free."

We replaced it with `dispatch_field_by_id<T>(id, fn)` - a single fold
expression instead of a recursive restart, in a form the compiler can
collapse into a jump table the same way it does for a regular `switch`:

```cpp
template<class T, class Fn, std::size_t... Is>
[[gnu::always_inline]] constexpr bool dispatch_field_by_id_impl(
    std::uint64_t id, Fn& fn, std::index_sequence<Is...>) {
    bool found = false;
    auto try_field = [&]<std::size_t Index>() {
        if (found || static_cast<std::uint64_t>(field_at<Index, T>().id) != id) {
            return;
        }
        fn(field_at<Index, T>());
        found = true;
    };
    (try_field.template operator()<Is>(), ...);
    return found;
}
```

Without `always_inline`, this whole construct wouldn't have been worth
rewriting: the compiler unrolls the fold right back into a chain of
sequential comparisons inside `read_message` - in terms of generated code
that's indistinguishable from the old recursive version, it just looks
more compact in the source. The marker in the code looks like a stylistic
detail, but it's exactly what turns the fold into a dispatcher that
actually collapses into a jump table on wide messages.

We didn't just eyeball it: a benchmark run against real libprotobuf
confirmed no regressions across the whole set of scenarios.

## Where It Didn't Work Out: `int25` and `vector[100]`

We tried two alternative ways of decoding varints for these two
scenarios - a branchless SWAR decoder handling several bytes at once, and
replicating libprotobuf's own single-byte fast path. Both measured worse
than what was already there, given the real value distribution in this
codebase. Dragging in a more complex decoder for two scenarios out of
fourteen seemed unjustified - we decided to just clearly document the
boundary of applicability.

## Bottom Line

There's no secret trick here - there's one cause (a window instead of an
intermediate buffer) and two direct consequences: no memcpy when encoding
a field, and no size pre-pass over the message, except for the single spot
where the protocol itself requires it - and there, an expensive pass was
simply swapped for a cheap one. Plus a separate finding on the read side:
a linear fold instead of a quadratic field search. Together that's enough
to beat generated protoc code almost everywhere, save for a couple of
clearly documented exceptions.

The binary adapter provides a useful comparison: when compatibility with
someone else's format isn't needed at all, CONTRACT has its own wire
format, with no regard for protobuf. Where there's no need to accommodate
someone else's design decisions, the contract layer costs literally zero
on top of hand-written C++ code - the ratio sits around 1.00 for nearly
every type and access path (`docs/reference/benchmarks.md`). With protobuf
everything is harder precisely because the format belongs to someone
else: it has its own wire-level constraints (the same `int25`/`vector[100]`
case), and there's no removing them without breaking compatibility. If
you're curious about the binary adapter's details - let us know, we'll
cover it separately.
